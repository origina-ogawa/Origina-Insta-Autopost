# 第1・2幕のディレクトリ運用整備(雛形のみ)

作成日: 2026-08-13

## 背景

`docs/superpowers/specs/2026-08-12-act5-publish-trigger-design.md` の「未解決事項」に、以下が
「別プロジェクトとして後日扱う」と明記されていた。本ドキュメントはそのうち、

- `sources/` の雛形
- `work/<slug>/` の雛形
- ブランチ運用(`post/YYYY-MM-DD-<slug>`)のドキュメント化

を扱う。**正式な設計ブレストを経ていない領域のため、大きな構造変更はせず、最小限の雛形とドキュメント追加に留める。**
判断に迷った点は「未解決事項」としてこの下にまとめ、社長の確認を待つ。

## 今回やったこと

- `sources/README.md`: 一次ソースの置き方・命名規則(`sources/YYYY-MM-DD-<slug>.md`)を記載。
  内容の形式は既存の `researcher.md` の出力例をそのまま踏襲した(新しい形式は作らない)
- `work/.gitkeep`: `work/` ディレクトリの存在を示すファイルを追加。`.gitignore` を
  `work/*` + `!work/.gitkeep` に変更し、`work/` 配下の作業ファイルはこれまで通りgit管理外のまま、
  ディレクトリ自体だけはリポジトリに残るようにした(重複していた `.gitignore` の記述もついでに整理した)
- ブランチ運用のドキュメント化(下記)

## ブランチ運用(`post/YYYY-MM-DD-<slug>`)

`CLAUDE.scaffold.md` に「作業ブランチ: `post/YYYY-MM-DD-<slug>`」「`main` への直接コミット禁止」と
あるが、**どの幕が・いつブランチを切るか**は明記されていなかった。現時点の理解を整理する。

- `sources/` は一次ソースであり、`AGENTS.md` の分離表では「コミットする」対象。ただし第1幕(researcher)の
  時点ではまだ投稿が採用されるか未確定(3件集まらない場合は不採用もありうる)ため、
  **`sources/` への追加は `post/<slug>` ブランチ上で行い、まだ `main` にはマージしない**運用を想定する
  (`main` に混ざるのは publisher の PR がマージされた時点)
- `work/` はgit管理外なので、どのブランチで作業していても影響しない
- ブランチを切るタイミングの候補は2つあり、今回はどちらか決め切っていない:
  1. researcher が第1幕開始時に `post/<slug>` を切る(ソース収集の時点からブランチが存在する)
  2. director が第2幕(構成案)を書く時点で切る(第1幕はブランチ無しでローカル作業、承認後にブランチ化)
  いずれも一長一短があるため、**「未解決事項」として社長の判断を仰ぐ**
- `posts/YYYY-MM-DD-<slug>/` への移動(inspector担当)、PR作成(publisher担当)は
  すべて同じ `post/<slug>` ブランチ上で行う(`publisher.md` に既に明記されている内容と一致)

## 未解決事項(社長への確認事項)

1. `post/YYYY-MM-DD-<slug>` ブランチをどの幕・どのタイミングで作成するか(上記2案のどちらか、または別案)
2. リサーチの結果テーマが不採用になった場合、そのブランチ・`sources/` ファイルはどう扱うか
   (ブランチを消す/`sources/`に残したまま次回流用する、など)
3. 複数の投稿を並行制作する場合、`work/<slug>/` はslugで分かれるので衝突しないが、
   `sources/` は同じ日に複数テーマを扱うとファイル名の衝突は起きない(slugが違えば別ファイル)ものの、
   運用上どこまで並行を許すかは未整理

これらは実際に第1・2幕を手動運用してみてから判断する方が精度が高いと考え、今回は雛形とドキュメントの
追加のみに留めた。
